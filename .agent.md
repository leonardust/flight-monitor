# 🚀 PR Creator Agent

Automatyzuje tworzenie Pull Requestów z gotowych zmian oraz obsługę review feedback.

⚠️ **WAŻNE**: Wszystkie generowane zmiany muszą być zgodne z [DEVELOPMENT-GUIDELINES.md](.github/DEVELOPMENT-GUIDELINES.md)

Czytaj:

- [`.github/skills/create-pr/SKILL.md`](.github/skills/create-pr/SKILL.md) — Tworzenie PR
- [`.github/skills/review-rework/SKILL.md`](.github/skills/review-rework/SKILL.md) — Obsługa review feedback

## Triggers

### 1. Utwórz PR

**Polecenie:** `utwórz PR` | `create PR` | `zrób PR`

Agent automatycznie:

1. ✅ Detektuje zmienione pliki
2. ✅ Sugeruje podziału na commity (dla dużych zmian)
3. ✅ Określa typ zmian (fix/feature/refactor/docs/chore)
4. ✅ Proponuje branch name wg Git convention
5. ✅ Tworzy commit(y) z konwencją `<typ>:<treść>`
6. ✅ Pokazuje PREVIEW do zatwierdzenia
7. ✅ Po potwierdzeniu (Y):
   - `git push origin <branch>`
   - Tworzy PR przez GitHub API
   - PR w statusie **OPEN** (nie draft)

**Przykład:**

```yaml
User: "utwórz PR"

Agent:
  Zmienione pliki: check-flights.js, check-flights.test.js

  Proponuję:
  ├─ Branch: fix/send-charts-only-on-change
  ├─ Commit 1: fix: send charts only on price change
  ├─ Commit 2: test: update chart notification tests
  ├─ PR Title: fix: send price charts only on price change
  └─ PR Desc: Wykresy z ostatnimi 10 cenami wysyłają się...

  Czy wysłać? [Y/n]

User: "Y"
Agent: ✅ PR Created! https://github.com/...

```

### 2. Commit i Push (bez PR)

**Polecenie:** `commit i push` | `commituj i push`

Skrócony workflow - commituje i pushe na **bieżącym branchu** (NIE tworzy nowego):

1. Detektuj zmienione pliki
2. Sugeruj commit message z konwencją
3. Commit zmienione pliki
4. Push na bieżący branch (np. `refactor/code-quality`)
5. **Brak PR** - dla wewnętrznych zmian, update istniejącego brancha

**Przykład:**

```yaml
User: "commit i push"

Agent:
  Branch: (bieżący branch)
  Commit: fix: send charts only on price change

  Czy wysłać? [Y/n]

User: "Y"
Agent: ✅ Pushed! origin/fix/send-charts-only-on-change

```

### 3. Napraw Review Feedback

**Polecenie:** `napraw review` | `fix comments` | `address feedback` | `rework`

Obsługuje review comments z GitHub PR:

1. ✅ Parsuje komentarze z wątku review
2. ✅ Identyfikuje typ feedback'u (TEST/SECURITY/REFACTOR/DOCS)
3. ✅ Implementuje poprawki
4. ✅ Weryfikuje vs [DEVELOPMENT-GUIDELINES](.github/DEVELOPMENT-GUIDELINES.md)
5. ✅ Uruchamia testy
6. ✅ Commituje zmiany
7. ✅ Auto-repond w wątku z krótką odpowiedzią
8. ✅ Zamyka wątek (resolve)

**Przykład:**

```yaml
PR #21 ma unresolved review thread:
  Copilot: "Please add coverage for unchanged price (no chart)
            and changed price with 2+ entries (chart sent)"

User: "napraw review"

Agent:
  Parsuje feedback → Typ: TEST
  Implementuje testy
  Uruchamia: node --test → 25/25 pass ✅
  Commituje: "test: add chart notification tests..."
  Pushuje zmianę
  Auto-reply: "✅ Dodane testy: ... Wszystkie testy pass: 25/25 ✅"
  [✓ RESOLVED]

Result: PR updated, thread closed ⏱️ ~2 min

```

**Więcej szczegółów**: [`.github/skills/review-rework/SKILL.md`](.github/skills/review-rework/SKILL.md)

## Workflow Szczegółowo

### Krok 1: Detektowanie Zmian

```bash
git diff --name-only origin/main HEAD

```

Wynik:

```sh
check-flights.js        ← zmiana w kodzie
check-flights.test.js   ← zmiana w testach

```

### Krok 2: Analiza Rozmaru

- **Małe** (1-3 pliki, < 50 linii): 1 commit
- **Duże** (4+ pliki, 50+ linii): sugeruj split

Agent pytań:

```html
Wykryłem duże zmiany w 4 plikach.

a) 1 commit: "refactor: improve notification system"
b) 2 commity:
   - commit 1: "refactor: extract chart logic" (check-flights.js)
   - commit 2: "test: update chart tests" (check-flights.test.js)
   - commit 3: "docs: update README" (README.md)
c) 3 commity: (dalszy split)

Która opcja? [a/b/c]

```

### Krok 2.5: Grupowanie Plików do Osobnych PR

**Dla wieloaspektowych zmian** - zaproponuj podział na logiczne grupy:

```ini
Wykryłem zmienione pliki w 3 kategoriach:

Grupa 1 - CODE:
  ✓ check-flights.js (zmieniony)

Grupa 2 - INFRASTRUCTURE:
  ✓ .agent.md (nowy)
  ✓ .github/skills/create-pr/SKILL.md (nowy)

Czy chcesz:
a) 1 PR - wszystko razem
b) 2 PR - osobne dla każdej grupy (REKOMENDOWANE)
c) CUSTOM - sam wybierzesz pliki do PR

```

**Jeśli c) - Custom Selection**:

```yaml
Wybierz pliki dla PR #1:
  [✓] check-flights.js
  [ ] .agent.md
  [ ] .github/skills/create-pr/SKILL.md

Wybierz pliki dla PR #2:
  [ ] check-flights.js
  [✓] .agent.md
  [✓] .github/skills/create-pr/SKILL.md

[OK] Dalej

```

**Rezultat**: N osobnych PR, każdy z własnymi commitami i metadanymi 📋

### Krok 3: Określenie Branch'a

Na podstawie commitów, automatycznie mapuje do branch'a:

| Typ      | Branch Prefix |
| -------- | ------------- |
| fix      | `fix/`        |
| feature  | `feature/`    |
| refactor | `refactor/`   |
| docs     | `docs/`       |
| chore    | `chore/`      |
| test     | `test/`       |

Opis: generowany z commit message, max 50 znaków

**Przykład:**

```sh
Commit: "fix: send charts only on price change"
Branch: fix/send-charts-only-on-change

```

### Krok 4: PR Metadata

- **Tytuł**: ogólny opis zmian
- **Opis**: krótki tekst wyjaśniający DLACZEGO (bez listy commitów)
- **Status**: OPEN (gotowy do review)
- **Base**: main
- **Compare**: feature-branch

**Przykład:**

```yaml
PR Title:
  fix: send price charts only on price change

PR Description:
  Wykresy z ostatnimi 10 cenami wysyłają się teraz tylko gdy
  cena się zmieni. Wcześniej wysyłały się przy każdym sprawdzeniu.

  Zmiana poprawia signal/noise ratio dla użytkownika.

```

### Krok 6: Git Operations

Jeśli "Y":

```bash
# 1. Pobierz najnowszą wersję main
git fetch origin
git checkout main
git pull origin main

# 2. Utwórz branch od świeżego main
git checkout -b fix/send-charts-only-on-change

# 3. Stage pliki
git add check-flights.js check-flights.test.js

# 4. Commit 1
git commit -m "fix: send charts only on price change"

# 5. Commit 2
git commit -m "test: update chart notification tests"

# 6. Push
git push origin fix/send-charts-only-on-change

# 7. Utwórz PR (GitHub API)
```bash
# Dynamicznie pobierz owner/repo
REPO_URL=$(git config --get remote.origin.url)
REPO_PATH=${REPO_URL##*github.com[:/]}  # "leonardust/flight-monitor"

curl -X POST \
  -H "Authorization: token $GH_PAT" \
  -H "Accept: application/vnd.github.v3+json" \
  https://api.github.com/repos/$REPO_PATH/pulls \
  -d '{
    "title": "fix: send price charts only on price change",
    "body": "Wykresy z ostatnimi 10 cenami...",
    "head": "fix/send-charts-only-on-change",
    "base": "main",
    "draft": false
  }'

```

## Konfiguracja

Agent używa zmiennych z `.env`:
- `GH_PAT` — GitHub Personal Access Token (do GitHub API)
- `GIST_ID` — (opcjonalny, nie potrzebny dla PR)

Wymagane permissions w `GH_PAT`:
- `repo` — dostęp do repo
- `workflow` — dostęp do Actions (opcjonalny)

**Pobieranie Git Info**:
- Repo URL: `git config --get remote.origin.url` → ekstrahuj owner/repo
- Bieżący branch: `git rev-parse --abbrev-ref HEAD`
- Remote main: `git rev-parse origin/main` → upewnij się że main istnieje

## Error Handling

| Problem | Rozwiązanie |
|---------|------------|
| Branch już istnieje | Agent sugeruje nową nazwę: `fix/send-charts-only-on-change-2` |
| Merge conflict | Agent zatrzymuje się i prosi o ręczne resolve |
| No changes | Agent przerwie: "Brak zmian do commita" |
| API error | Retry 3x z exponential backoff |
| Git not found | Komunikat: "Git nie jest zainstalowany" |

## Integracja z Workflow'ami

Po utworzeniu PR, GitHub Actions mogą:
- ✅ Uruchomić testy (`node --test`)
- ✅ Sprawdzić linting
- ✅ Zrobić code review (jeśli skonfigurowany bot)
- ✅ Auto-merge (jeśli approved)

## Troubleshooting

**Agent nie reaguje na trigger?**
- Sprawdź czy trigger zawiera dokładne słowa kluczowe
- Trigger jest case-insensitive

**PR nie wysłał się?**
- Sprawdź `GH_PAT` w `.env`
- Zweryfikuj uprawnienia tokena
- Sprawdź czy branch już istnieje na remote

**Commity w złej kolejności?**
- Agent automatycznie sortuje po `<typ>` (chore → feature → fix)
- Jeśli chcesz inne porządek, powiedz w preview
